= Analyze latency trends for EDA in Workload Factory
:icons: font
:imagesdir: ./media/

[.lead]
After a latency event is detected, use the interactive graph to see how latency and volume change over time. This helps you spot patterns, see if the problem happens often or only once, and decide how to fix it based on the data.

== Before you begin

You must have link:task-configure-latency-monitoring.html[configured latency monitoring] and at least one latency event detected.

== Analyze latency trends

The *Over time* tab provides performance graphs to help you analyze volume behavior: latency, IOPS, and throughput.

.About this task

The graphs show CloudWatch metrics for the affected volume. All graphs use the same timeline. They automatically display read or write metrics based on which alarm triggered the event.

You can change the time range to see performance over different periods. You can also switch between All, Read, Write, or Metadata operations.

The visualization includes:

* *Latency graph*: Shows actual latency values (in milliseconds) collected from CloudWatch over time with threshold lines and breach indicators.
* *IOPS graph*: Shows actual latency in milliseconds from CloudWatch over time. Threshold lines mark the set limits, and markers show when those limits were exceeded. It also shows operations per second with a threshold line and markers for past breaches. Read activity shows DataReadOperations, and write activity shows DataWriteOperations.
* *Throughput graph*: Shows data transfer rates. For read events, it displays DataReadBytes. For write events, it displays DataWriteBytes. If **Metadata** is selected in the filter, the throughput graph shows no data.
* *Threshold lines*: Dotted horizontal lines show the warning and critical limits you set on the latency and IOPS graphs.
* *Breach indicators*: Visual markers that show when thresholds were exceeded and how many times during the period.
* *Breach details*: For each breach, view the median delay, the percentage above the limit, QoS delay center data, and the time it was detected.

.Steps

. In the *Latency* tab, select a latency event from the events table.
+
The latency analysis panel opens.

. Select the *Over time* tab.

. Review the default view, which shows performance graphs for latency, IOPS, and throughput over the past 3 hours.

. Optionally, use the *Type* filter to switch between All, Read, Write, or Metadata operations. The default matches the event type (Read for read events, Write for write events).

. Change the time range to review other periods and look for patterns.

. Check the trend lines for latency, IOPS, and throughput. The IOPS and latency graphs include threshold lines for comparison.

. Look for breach indicators on the graphs. These markers appear when thresholds are exceeded multiple times during the selected time period.

. To see more details, hover over or select a breach indicator.

. Review the breach count summary:
+
The graph shows the total number of warning or critical breaches during the selected time period.

. Use the graph insights to:
+
* See whether latency issues happen once or occur repeatedly
* Identify times of day when latency is higher
* Determine whether latency spikes are short or long-lasting
* Compare latency events with workload patterns or system changes

.Result

You can see how latency for the volume changes over time. This helps you decide whether to take action now, change alert limits, or check for system issues.

NOTE: The latency graph uses CloudWatch metrics. These might be slightly different from ONTAP QoS delay center data because they are collected in different ways. Both are shown to give a more complete view.

== Graph interpretation

Use these tips when reviewing changes in response time:

* *Use multiple time frames*: Look at the graphs in different time ranges to tell the difference between brief spikes and ongoing slowdowns. Start with the 24-hour view for overall context. Then zoom in to shorter periods to examine specific incidents, or switch to the 72-hour view to spot daily patterns.

* *Compare thresholds visually*: Use the threshold lines on the graph to check if your warning and critical settings fit your workload. If latency often gets close to the threshold but does not cross it, the threshold might  be too high. If you see many short spikes that cross the threshold but do not affect operations, the threshold might be too sensitive.

* *Identify daily patterns*: Use the 24-hour and 72-hour views to spot patterns during the day. If latency spikes happen at the same times, schedule heavy tasks during quieter periods or add more capacity for busy times.

* *Distinguish spike types*: Short spikes usually mean temporary issues, such as brief resource contention. Latency that stays high over time points to deeper system problems, like limited capacity or configuration issues. Each situation needs a different fix.

* *Monitor trends after changes*: After adjusting thresholds, adding capacity, or changing settings, monitor the graph for at least 72 hours to make sure the changes worked.
